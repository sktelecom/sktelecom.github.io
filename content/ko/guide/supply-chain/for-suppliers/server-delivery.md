이 문서는 OS 위에 애플리케이션을 얹어 서버 형태로 납품하는 공급사를 위한 심화 가이드입니다. 일반 애플리케이션 납품이라면 [SBOM 생성 방법](../creation-guide/)만으로 충분합니다.

서버 SBOM은 납품되는 상태의 rootfs나 이미지를 한 번 스캔하는 것이 기본입니다. 이 한 번의 스캔에 OS 패키지와 그 위에 설치된 애플리케이션 의존성이 함께 담깁니다. 다만 두 가지는 이 스캔으로 잡히지 않아 따로 만들어 합쳐야 합니다. 빌드 도구가 해석해야 하는 의존성(Maven, Gradle 등)과 정적 링크된 라이브러리입니다. 정적 링크를 빠뜨리는 것이 서버 납품에서 가장 흔한 반려 원인입니다.

## 서버 SBOM에 담겨야 하는 것

| 구분 | 대상 | 누락 시 증상 |
|----|------|--------------|
| OS 패키지 | rpm/dpkg/apk 데이터베이스에 등록된 패키지 전체 | OS 취약점 누락 |
| 애플리케이션 의존성 | 납품 애플리케이션과 패키지 매니저 의존성(직접·전이) | 앱 의존성 누락 |
| 정적 링크 라이브러리 | 빌드 시 바이너리에 포함된 openssl 등 | 어느 스캔에도 잡히지 않음 |

## 기본: 납품 상태를 한 번에 스캔

서버의 rootfs(추출한 루트 파일시스템)나 그 컨테이너 이미지를 Syft로 스캔합니다. 패키지 데이터베이스(rpm/dpkg/apk)를 읽어 설치된 패키지를 모두 실제 purl(`pkg:rpm/...`)로 식별하고, 같은 스캔에서 애플리케이션 의존성도 함께 수집합니다.

```bash
# rootfs 디렉터리를 대상으로
syft dir:/path/to/server-rootfs -o cyclonedx-json=server_bom.json

# 서버가 컨테이너 이미지로 패키징돼 있다면
syft myserver:7 -o cyclonedx-json=server_bom.json
```

대상은 받아온 원본 베이스가 아니라 빌드가 끝나 납품되는 상태여야 합니다. 빌드 과정에서 설치한 OS 패키지까지 포함해야 하기 때문입니다.

대상에는 패키지 데이터베이스가 있어야 합니다. 설치 파일만 풀어 놓고 rpm 데이터베이스가 없는 폴더를 스캔하면 purl이 비어 반려됩니다.

{{% alert title="애플리케이션 소스만 스캔하면 OS 패키지가 통째로 빠집니다" color="warning" %}}
서버 납품인데 애플리케이션 소스 트리만 스캔해 제출하는 사례가 반복됩니다. 이 경우 설치된 rpm 패키지가 하나도 담기지 않아, OS를 업그레이드해도 그 결과가 SBOM에 나타나지 않습니다. 스캔 대상이 납품 상태의 rootfs나 이미지인지 먼저 확인하시기 바랍니다.
{{% /alert %}}

## 따로 만들어 합쳐야 하는 경우

### 빌드 도구가 해석하는 의존성

Maven이나 Gradle처럼 의존성이 프로젝트 밖 로컬 저장소에 놓이는 경우, rootfs 스캔이나 Syft의 소스 스캔만으로는 직접 선언한 라이브러리까지만 잡히고 전이 의존성이 빠집니다. 애플리케이션 소스에서 cdxgen으로 따로 생성합니다.

```bash
cd /path/to/app-source
cdxgen -o app_bom.json
```

매니페스트가 없는 순수 CMake/Make 애플리케이션은 컴포넌트 목록이 희소해집니다. 이 경우 아래 정적 링크 절을 함께 적용하시기 바랍니다.

### 정적 링크 라이브러리 (사각지대)

정적 링크된 라이브러리는 패키지 매니저가 선언하지 않고 OS 패키지 데이터베이스에도 올라 있지 않아, 어느 스캔도 잡지 못합니다. 완전 자동 경로가 없으므로 두 가지를 함께 씁니다. 도구가 찾을 수 있는 만큼은 납품 바이너리를 분석하고, 그래도 빠지는 부분은 빌드 스크립트에서 소스와 버전(예: `openssl 1.1.1za`)을 직접 기재합니다.

```bash
syft file:/path/to/delivered-binary -o cyclonedx-json=static_bom.json
```

정적 링크 구성요소의 정밀 식별은 바이너리 구성 분석(BDBA)의 몫이며, SK텔레콤이 보완 검증으로 수행합니다.

## 하나로 합쳐 제출

SK텔레콤 제출 시스템은 제품당 SBOM 하나를 등록합니다. 위에서 따로 만든 SBOM이 있으면 `cyclonedx-cli`로 합쳐 단일 BOM으로 제출하고, 최상위 컴포넌트를 납품 제품명·버전으로 기재합니다. 병합 시 purl이 같은 컴포넌트는 한 번만 집계되므로 둘 이상에 나타나는 라이브러리가 중복되지 않습니다.

```bash
cyclonedx-cli merge \
  --input-files server_bom.json app_bom.json static_bom.json \
  --output-file myserver_1.0.0_bom.json \
  --name myserver --version 1.0.0
```

- [cyclonedx-cli](https://github.com/CycloneDX/cyclonedx-cli): CycloneDX 공식 명령행 도구

{{% alert title="검토용으로 스캔별 SBOM을 함께 보관하세요" color="info" %}}
공식 제출물은 병합된 단일 BOM이지만, 병합 전 SBOM은 어느 부분이 누락·취약한지 바로 보여 주므로 자체 검토와 재제출 대응에 유용합니다. 함께 보관하시기 바랍니다.
{{% /alert %}}

## 클러스터·다중 노드 구성이라면

여러 대의 노드가 하나의 클러스터를 이루는 제품도 제출 단위는 동일하게 제품당 SBOM 하나입니다. 노드 대수만큼 만들 필요는 없습니다.

*   모든 노드가 동일 구성이라면, 대표 노드 1대를 기준으로 생성과 병합을 진행합니다.
*   노드 역할에 따라 설치된 소프트웨어가 다르다면(예: 관리 노드와 스토리지 노드), 역할별로 만든 뒤 전체를 병합해 하나로 제출합니다.

## 제출 전 검증

병합 전후 SBOM 모두 컴포넌트가 실제 purl을 갖는지 확인해야 합니다. 확인 명령과 점검 항목은 [검증 체크리스트](../checklist/)를 따르십시오.
